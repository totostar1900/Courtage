# Plan — étude IFC en ligne

Spécification : `docs/specs/2026-09-26-plateforme-et-etude-ifc-design.md`.
Méthode : tests d'abord, suite verte avant chaque commit, un commit par tâche
avec le message indiqué.

## Tâche 1 — Moteur actuariel et tests de référence

- [x] Squelette `api/` (pyproject, src/courtage, pytest).
- [x] Référentiel minimal en fichiers : table TV CIMA F, barème CCI Côte
      d'Ivoire (`valide`), barème APB Madagascar (`valide`), turnover plat 2 %.
- [x] `courtage.actuariat.ifc.evaluer()` : fonction pure, détail par salarié,
      totaux entiers.
- [x] Fixture AZITO (23 salariés au 31/12/2019, probabilités de présence du
      classeur).
- [x] Tests : réplique du classeur (CI), réplique du rapport 2023 (APB),
      présence calculée, salarié au-delà de la retraite, barèmes unitaires,
      cotisation nulle quand le fonds couvre.

Commit : `feat(actuariat): moteur IFC et tests de référence AZITO`

## Tâche 2 — Référentiel versionné

- [x] Format d'un barème validé par Pydantic : pays, code, statut, vigueur
      (du … au …), sources citées, note de vérification, barème typé
      (`tranches_cumulatives` | `paliers`). Tranches et paliers ordonnés,
      taux bornés, vigueur cohérente.
- [x] Chargement d'une version complète ; refus d'un barème mal formé et de
      deux versions d'une même convention qui se chevauchent.
- [x] Barèmes camerounais trouvés en ligne : commerce 2012 et 2024
      (changement au 16/01/2024), banques 2021 (`valide`) et 2024
      (`a_valider` : révisée le 18/11/2024, barème non publié).
- [x] `motifs_de_refus(convention, pays, date)` : `pays_different`,
      `convention_a_valider`, `hors_vigueur`.

Commit : `feat(referentiel): versions, barèmes et règle d'émission`

## Tâche 3 — Lecture et contrôle du fichier du personnel

- [x] Lecture xlsx et csv (`;` `,` tabulation ; UTF-8 ou Windows) ; ligne de
      titre tolérée au-dessus des intitulés ; colonnes reconnues par leur
      intitulé en français ou en anglais ; salaire mensuel ou annuel, dit par
      l'intitulé ou par le dépôt, contradiction bloquante.
- [x] Colonnes de nom repérées et ignorées : leurs valeurs ne sont jamais lues.
- [x] Contrôles bloquants et avertissements de la spec §6, chacun testé ; en
      plus : matricule en double, date illisible (année sur deux chiffres
      refusée), deux colonnes pour un même champ.
- [x] Chaque anomalie porte son niveau, son code, un message, la ligne telle
      que l'utilisateur la voit dans son tableur, et la colonne.
- [x] Bout en bout : le fichier AZITO, présenté comme une DRH l'enverrait
      (avec des noms), redonne la dette du moteur.

Reste pour la tâche 5 : l'écart de plus de 25 % avec l'étude précédente
(il faut l'étude précédente, donc la base).

Commit : `feat(fichier): lecture et contrôle du fichier du personnel`

## Tâche 4 — Base de données

- [x] SQLAlchemy 2 + Alembic ; migration `0001_socle` écrite à la main en SQL
      (schéma, RLS, droits, déclencheurs) ; modèles SQLAlchemy vérifiés contre
      le schéma migré.
- [x] Rôle applicatif `courtage_app` distinct du propriétaire ; RLS par
      `organisation_id` sur les fichiers, les études et le journal ; contexte
      posé par transaction (`contexte()`), perdu à sa fin.
- [x] `journal`, `fichiers_personnel` et `sceaux` en ajout seul pour le rôle
      applicatif ; une étude émise immuable pour TOUS les rôles (déclencheur) ;
      une étude émise porte ses résultats, son empreinte, son émetteur.
- [x] Tests : une organisation ne lit ni n'écrit chez une autre ; sans
      contexte on ne voit rien ; montants entiers et positifs.

Écart à la spec §5 : le référentiel reste en fichiers versionnés dans le code
(tâche 2) plutôt qu'en tables. Une étude enregistre la version du
référentiel, le code de la convention et la date d'effet de son barème, ce qui
suffit à la refaire. Les identités (organisations, utilisateurs, adhésions) et
les sceaux sont hors RLS : ils sont lus avant qu'une organisation soit choisie,
ou par la vérification publique.

Commit : `feat(db): schéma, RLS et verrous d'immuabilité`

## Tâche 5 — API de l'étude, avec la rémunération

- [x] Migration `0002_remuneration` : conditions de rémunération par client
      (`honoraires` | `commission` | `mixte`, forfait par étude, part par
      salarié, commission en points de base), en ajout seul, datées ; le mode
      doit concorder avec les montants. Une étude émise porte ses conditions et
      ses honoraires HT.
- [x] FastAPI sous `/api/v1` ; une transaction par requête, droits vérifiés sur
      les adhésions, puis contexte RLS ; une erreur annule tout.
- [x] Organisations (plateforme), adhésions (plateforme ou conseiller), `/moi`.
- [x] Rémunération : fixée par le conseiller, lue par tout membre (la
      commission est publiée au client).
- [x] Dépôt d'un fichier → lecture, refus s'il est illisible, lignes gardées
      sans nom.
- [x] Brouillon : calcul, totaux, détail, échéancier des départs,
      sensibilités (taux ±1 pt, salaires +1 pt), anomalies, émission possible
      ou non avec ses motifs ; recalcul, suppression.
- [x] Hypothèses : le référentiel par défaut ; un écart exige une
      justification, enregistrée avec lui.
- [x] Émission par un conseiller seulement ; refusée (409, motifs) pour une
      anomalie bloquante, une convention d'un autre pays / à valider / hors
      vigueur, ou sans conditions de rémunération ; empreinte SHA-256.
- [x] Avertissement d'écart de plus de 25 % avec l'étude émise précédente.
- [x] Journal à chaque écriture.

Identité provisoire : l'en-tête `X-Utilisateur` en mode `entete_dev`, refusé
en production ; la tâche 8 le remplace.

Commit : `feat(api): parcours de l'étude IFC et rémunération par client`
